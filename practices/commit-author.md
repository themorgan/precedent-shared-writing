## Rule
Every commit I author carries the name and email `identity.json` declares, at the root of this set -- don't ask who the author is first, and don't write those values anywhere else. That file is the one place they live: the `SessionStart` hook reads it, the `env` block in this repo's `.claude/settings.json` derives from it, and this practice's own check reads it rather than restating it.

Nobody types a `git config` line for this. `bootstrap/commit-identity.sh` resolves the identity, sets it locally, and installs a `pre-commit` hook that refuses a commit whose author is anything but the declared one -- or is the container's own agent account, which is never a person.

## Detail
**Why one file rather than the four places these values used to sit in.** They were in this practice's own Rule, in the `env` block, in the check that enforces it, and in the hook -- so "change my address" meant four edits, three of which nothing would have caught if missed. `identity.json` is the declaration; everything else derives from it or is checked against it. The mechanism is generic rather than a personal arrangement: the same hook and the same two check scripts, copied into anybody else's individual set, read *their* identity.json and enforce *their* declaration.

This replaces only the *identity* half of the generic default of asking before the first commit. It says nothing about co-authorship: a host's own `Co-Authored-By:` trailer naming the assistant still applies undisturbed alongside it.

The same identity extends past the git config lines themselves: commits, PRs, and any GitHub-side attribution are mine under the `themorgan` account.

**How to refer to me in prose used to be a clause of this paragraph, and is not this practice's business.** It said to use "Morgan" and he/him. It moved to `identity.json`'s own `pronouns` field on 2026-09-12, under the universal practice `declared-pronouns`, because a rule about how to write about a person was reachable only by reading a git-config practice to the end -- and, being prose in my private set, answered the question for me while leaving it unanswered for everyone else. This practice is about commit authorship alone.

## Why
The identity is already decided, every time -- there is nothing to ask about, and asking on every fresh clone is pure friction for a fact that never changes.

**The bigger reason sits above the friction one: in a group or team repository, a commit's author is how the other people there know who did the work.** A tree of commits authored `Claude <noreply@anthropic.com>` erases that -- every session looks identical, and nobody reading the log later can tell which of several people (or which of their sessions) made a given change. Attributing to the real person is what keeps `git log`, `git blame`, and GitHub's own contributor view answering "who did this" correctly once more than one person is committing. Morgan, 2026-09-15.

## Story
Written down after the identity question got asked, and answered the same way, often enough that answering it was clearly more session time than the fact was worth.

**2026-09-06: six commits later, the instruction was replaced by a mechanism.** `aa2155d` landed as `Claude <noreply@anthropic.com>` on 2026-09-04 and was grandfathered as a one-off session mistake. Five more did the same thing over the next two days (`977e360`, `b40a903`, `7fb401f`, `4659596`, `b25b69a`), which is the point at which "a session forgot" stops being a fair description of what is happening. A hosted container asserts a *global* git identity of `Claude <noreply@anthropic.com>` at every session start, deliberately, so that its commit signatures verify. This practice was asking a person or an agent to notice and override that default, per clone, before the first commit, forever -- and losing, one time in every few. Morgan's instruction was to grandfather the five rather than rewrite (the oldest is `977e360`, so a rewrite would have moved eighteen commits and broken `git pull --ff-only` in every existing clone, silently, since the bootstrap hook swallows that failure) and to fix it forward instead. See `bootstrap/commit-identity.sh`'s own header for why the fix takes three layers and what each one covers that the others cannot.

## Install
Three layers, wired once per project, never typed again. `bootstrap/commit-identity.sh` here is a copy of BestPractice's own adapter hook (`templates/harness/claude-code/hooks/commit-identity.sh`) and carries no personal value at all -- another project installs it from there, with the rest of that adapter, rather than from this private set. That gives: the `env` variables, which outrank git config and follow the session into a repository attached mid-session -- one that never runs its own `SessionStart` hook and so cannot be reached by a hook at all; the local `git config` the hook sets, for any path that does not read Claude Code's settings; and the `pre-commit` hook it installs, which checks what git is about to record rather than what was configured, and refuses the commit if it is wrong. The `env` block is the one derived copy of the declared values, and it exists only because a hook cannot reach a sibling repository; `check_commit_author.py` fails if it ever disagrees with `identity.json`.

`GIT_COMMITTER_*` is deliberately left alone: a hosted container's signing key is registered to its own address, and overriding the committer would make every commit show as Unverified on GitHub while changing nothing about authorship. This repo's own history is already that shape -- authored by Morgan F, committed by someone else.

The `env` layer is declared configuration rather than something this session could observe taking effect (settings are read at session start), so the `pre-commit` backstop is what makes relying on it safe: if `env` did not apply for any reason, the commit is refused rather than silently mis-authored.

Checked mechanically by [`tools/checks/check_commit_author.py`](../tools/checks/check_commit_author.py): every commit reachable from HEAD must carry the identity `identity.json` declares as its recorded author. Scope is `tree` -- `ROOT`'s own history, where `ROOT` is this repo when the check runs here in place, and the consuming repo when materialized into one (see the SOURCE_ROOT/ROOT split at the top of the script). Two-direction tested in [`tools/checks/tests/test_commit_author.sh`](../tools/checks/tests/test_commit_author.sh): a scratch copy with a planted wrong-author commit fails the check; the real, current history stays clean. The check's `GRANDFATHERED_SHAS` mechanism exempts an already-published commit by SHA rather than rewriting history to silence it -- see `no-rewrite-for-warnings` (BestPractice universal). Six commits sit in that list today: `aa2155d` (2026-09-04) and the five of 2026-09-05/06 named in the Story above, all grandfathered on Morgan's explicit instruction. Two earlier ones (`ac525c9`, `0016903`) were instead rewritten in place on 2026-09-03, also on his explicit instruction; the list emptied then and refilled twice over, which is the history that produced the mechanism in the Install section above. Every commit made after that mechanism landed is fully checked, and the check now also verifies the mechanism itself -- but only where it is installed, so a consuming repo that has not adopted it yet is not failed for that.

**2026-09-07: a second, per-repo exemption list, because the first one can't reach a consuming repo's own history.** `GRANDFATHERED_SHAS` above is this SET's own history, hardcoded -- fine as long as the check only ever audits the repo it ships in. The first real consumer to need this (`themorgan/HavrutaBrainstorm`, two commits, `209fa79` and `cd55422`, both from 2026-09-01/02, before this mechanism existed anywhere) can't add to that set: `tools/checks/` in a consuming repo is `precedent_materialize.py`'s own output, rewritten from this source on every sync, so an edit there is erased. `identity.json` is already the one per-`ROOT` file this check reads -- an optional `grandfathered_commit_shas` array there is the same mechanism, one level down: `{"sha": <40-hex>, "note": <why>}` entries, additive to `GRANDFATHERED_SHAS`, checked and shared with `buenos-aires-dates`'s identical field (that practice lives only in Morgan's individual source, not here) (one incident is usually wrong on both counts at once). A malformed entry -- no `sha`, not 40 hex characters, no `note` -- is reported as a finding rather than silently dropped; a grandfather list that can silently fail to exempt anything is worse than no list at all. Two-direction tested alongside the existing suite in the same test files: a planted commit whose SHA is declared is exempted, a malformed entry is flagged.

**2026-09-10: the check stops requiring a root `identity.json`, because in a shared repo it is forbidden.** The two statements this file made were incompatible. The check reported a violation when no `identity.json` sat at `ROOT` -- "it is the one place this repo's name, address and timezone live, so nothing downstream can be checked without it" -- while the paragraph above says a *shared* consuming repo must not have one at all, since an `identity.json` at a root is what declares "this repository is somebody's individual practice source" and putting one in a shared repo pins one person's identity onto everyone committing there. Both checks were therefore permanently red in every shared consumer, with the fix forbidden by the same file that demanded it; found installing Precedent into a real private project, where the install ended on exactly these two violations. The engine now answers the question instead: `precedent_resolve.declared_identity(repo)` resolves the person the way `commit-identity.sh` does -- a `PRECEDENT_COMMIT_*` override, then this repo's own `identity.json`, then the individual source the user-level config names -- and raises `NoDeclaredIdentity` when none of the three does. Neither check re-derives that. Where nothing resolves, the check reports SKIPPED (exit 2) rather than a violation: a violation must mean "a commit here has the wrong author", never "this repository is shared". A finding now also names *where* the expected identity came from, so it can be argued with. The import is guarded and reports SKIPPED with the reason where no engine module supplies the resolution at all.

**2026-09-10, same day, second revision: which module.** The helper first landed in `precedent_resolve.py`, which is in upstream's `CONSUMER_ENGINE_FILES` and deliberately not in its `ENGINE_FILES` -- a practice set resolves no catalogue, so a set does not vendor it, and both checks went from enforcing to SKIPPED inside the very set they belong to. Upstream moved the resolution into `precedent_identity.py`, which **is** in `ENGINE_FILES`, on the grounds that identity is a question about a *person* and a practice set is the one repository that most certainly has one. Both checks import `precedent_identity` first and fall back to `precedent_resolve` only for a consuming repo whose vendored engine predates the split. Anything in these sets that needs an identity imports `precedent_identity`; the resolver answers questions about a catalogue. This repo's own engine still predates it, so the checks stay SKIPPED here until a vendored-engine refresh -- see `TODO.md`.
